# M1522n print pipeline audit — 2026-10-26

## Evidence (Windows + MiniBox, not assumptions)
- Windows 10 queue `M1522n NET` uses Microsoft IPP Class Driver with WSD port.
- Windows PrintService/Operational 2026-10-26 local time: jobs 8, 9, 10, 11, 12; job 9 has Event 824/842 error `0x80070BCC` at 18:37:33 and Event 842/307 success at 18:38:50; job 11 error at 18:41:07 and success at 18:42:43. Event 307 reports spooler completion, not proof of paper physically exiting.
- Device journal (GMT) repeated 4960x7015, 600 dpi, 24 bpp PWG images; JPEG 6,110,486 bytes with 64.5–94.4 s encode time.
- USB failed at 5,551,090 of 6,110,984 requested bytes (`-7` libusb TIMEOUT) on some attempts; successful transfers of 6,111,021 bytes had matching transmitted/accepted hashes.
- Owner confirmed physical pages printed with grayscale halftones and reasonable preliminary quality; direct HP driver comparison is deferred.
- Distinct Windows job IDs are not, by themselves, duplicates of one submitted job; a repeated filter dispatch within the *same* job ID is concrete evidence of retry. Correlating a particular IPP request to a Windows job ID requires further data.

## Source audit (branch work/m1522-protocol-correct)
1. `src/minibox-usb/libusb_m1522.c`: returns progress when a timed-out transfer reports `done>0`; this prevents automatic resending the acknowledged prefix. Zero-progress timeouts still fail. Do not blindly resend an entire buffer or full PCL document after a partial USB transfer.
2. `src/minibox-usb/print_m1522.c`: bounded bulk wait has been raised 5000 -> 30000 ms in commit `42431126`. This is an unvalidated hardware mitigation, not proof of root-cause repair. USB slow/error logging is present.
3. `src/minibox-printerd/main.c`: chunked PWG path currently returns `ipp_reply(...,0x0400)` for any `prc != 0`, even when underlying error is USB transport, misclassifying a device/server error as client bad request. Same issue on content-length PWG path. Classify conversion, input/framing and hardware errors separately before changing status codes.
4. `src/minibox-printerd/main.c`: reports IPP job-state 9 immediately after stream-to-USB succeeds; it cannot guarantee the paper actually exited the printer. Avoid representing that as device-confirmed physical completion.
5. Client peer IP, IPP operation, request-id and USB timing were added in commits `26ff5139`, `1bc8bc46`, `cc4fc94e`, respectively, but cannot be observed on existing un-updated hardware yet.
6. Main event loop serializes print connections; long JPEG encoding blocks servicing new jobs, exacerbating client retries. Do not add concurrency without hardware USB serialization and resource bounds, and do not change captured PCL XL operators or the working halftone conversion speculatively.

## Correction and verification order
1. Protect the functioning single-block PCL XL/JPEG stream and native-HP capture compatibility. No speculative 128-row splitting or geometry changes.
2. Add regression test with a mocked USB sink: partial-success, zero-progress timeout, mid-page timeout, successful write; verify accepted prefix is never resent, byte hashes and returned status accurate.
3. Separate PWG parse/encode errors from USB I/O errors in server response logic; preserve explicit uncertainty of physical delivery and avoid silent fake success. Test Windows retry behavior without automatically dropping intentional duplicate prints.
4. Benchmark `IPP receive`, `PWG decode`, `JPEG encode`, `USB bulk`, and `post-USB physical paper delay` independently. Input 63,475,238 bytes per job, JPEG 6,110,486 bytes, encode 65–94 seconds; the conversion stage is a confirmed performance bottleneck.
5. Only after firmware image checks, preserving configuration and explicit authorization, validate on real HP M1522n: one job -> one printed page, acceptable time, no `-7`, correct halftones, operational scanner/Wi-Fi STA/WSD/mDNS/Web UI.

## Safety
No physical flashing, resetting, wiping queues or configuration; GitHub CI green alone is not hardware acceptance.
